## 核心體驗
清理出可用空間 → 自選修復順序 → 觀察掌櫃回應 → 對話並採取行動 → 完成修復 → 回訪看見居民使用成果。
成功不是得到一句感謝，而是玩家能指出自己改變了什麼，以及掌櫃為什麼這樣回應。

## 場景與操作
可見區域：門前、窗邊座位、櫃檯、煮茶區。沒有獨立室內載入、戰鬥、體力、睡眠或日曆。
〔改〕基本輸入：選取物件、查看、執行修復步驟、對話、離開／返回茶館。比賽版不做角色移動與自由搬放。
〔新〕點選本身不是問題，無意義的點擊才是：每一下都必須改變場景，不設同一處重複點擊的工序。
三個可任選順序的修復項目（〔新〕每項 2–3 步，工序為暫定）：
1. 門燈：扶正燈架 → 用場景裡回收的木料補好 → 點亮；改變入口照明與鬼客出現條件。
2. 茶具與煮水設備：撿回散落茶具 → 修好爐座 → 茶具歸位、生火；改變供茶能力與掌櫃可做的工作。
3. 候客區：清走雜物 → 把桌椅放到窗邊或火盆旁；改變停留位置。
三項材料各在本場景可取得，不靠重複刷取或等待。實際工序是否有趣須測試，不能把點擊數當努力感。
佈置選擇是同等有效結果，不設隱藏正解。

## 事件與進度：規則所有
事件紀錄包含單調遞增event_id、事件種類、對象及必要資料。〔改〕保存修復步驟與完成、家具位置、鬼客到訪、對話；比賽版不記錄承諾。
三處修復均完成即達成環境恢復；模型不得阻止完成。
角色恢復階段由可見里程碑推進：戒備 → 能合作 → 不再阻攔客人。模型決定階段內的表達與合法行為，不可自行跳階段或倒退鎖死進度。
先修燈：街上鬼客出現，尚缺設施時停在門口，形成是否及如何先接待的事件。
先修茶具：掌櫃可先恢復準備茶的工作，之後點燈才出現待客事件。
這些觸發條件由規則控制，模型解讀背景並選行為；不得把隨機差異說成因果。

## 對話〔改〕
玩家可自由輸入；另提供少量快捷說法供不想打字者使用。
〔延後〕可追蹤承諾（v0.1「對話與承諾」其餘內容）整段延後到賽後，原文保留在 v0.1。
比賽版中，玩家說出的約定只是對話，不宣稱已建立可追蹤任務；沒有隱藏逐字口令或某句話永久鎖死。

## AI 的職責與邊界
輸入：角色設定、當前恢復階段、世界狀態與狀態版本、帶id的事件、玩家訊息。
〔改〕輸出（以 JSON schema 約束格式）：
- line：掌櫃台詞，最多兩句
- attitude：暫時態度，固定選項
- references：最多兩個事件 id
- action：最多一個行動提案，或不行動
〔改〕狀態版本不由模型回傳：程式為每個請求保存請求 ID 與發送時的狀態版本，不採信模型自稱的版本。
〔改〕事實由規則呈現：台詞要求只表達當下感受、需求與意圖，不敘述過往事件。這是模型行為要求，不保證完全遵守；模型違規由測試記錄。歷史事實另由程式依 references 從事件紀錄產生，顯示在台詞下方的「相關事件」區塊。程式保證事件內容真實，但模型選了哪個事件，不代表引用一定恰當。
〔新〕JSON schema 只管格式，不保證內容真實：引用的 id 存在，不代表那個事件支持台詞的意思。檢查分兩類：
- 程式可擋下：格式錯誤、引用不存在的 id、行動不符前置條件、請求已過期或已逾時。一律不套用，不改動狀態。
- 程式無法可靠判斷：台詞是否把猜測說成已發生的事、引用的事件是否支持台詞。在模型層測試由人工標記並計數，文章如實寫成未解決的限制，不宣稱已解決。
可選行動：留在櫃檯、走向門口、準備茶、邀請入座、在門邊接待、〔新〕請客人稍候、請求協助。
〔新〕請客人稍候：須客人在場；鬼客改停在門外長凳等候（靜態圖層）。用途是讓接待、暫候、不介入三種意圖各有看得見的結果，而不是只差在台詞。
門外長凳是原本就能使用的臨時等候處，不屬於可修復的室內候客區；坐長凳不代表已被接待，也不取代修好座位。三個行動的畫面要能區分：
- 暫候：鬼客留在門外長凳，尚未正式接待。
- 接待：掌櫃移到門邊與客人互動。
- 邀請入座：鬼客進入修好的室內候客區。
行動前置條件由程式驗證，例如準備茶須設備已修；邀請入座須候客區完成且客人在場。
態度是角色詮釋而非新事實；歷史事實只能來自已存在事件，不接受模型創造修復紀錄。
模型僅在重要事件或玩家對話時呼叫，不逐幀推論。回應等待期間允許繼續修復。
〔改〕過期政策（比賽版單一規則）：
- 回應到達時，若目前狀態版本與該請求發送時不同，整份回應不套用（台詞與行動都不採用）。
- 同一時間最多一個有效請求；等待期間發生的新事件先累積，回應處理完後再合併成一個新請求。
- 逾時即標記該請求失效；之後才到的回應一律不套用。
格式錯誤、無效事件引用或逾時：採安全待機/固定短回應，保留成果、可重試，介面標示降級；不得把備援腳本展示為真實模型成果。

## 技術現況〔新，取代 v0.1「具體模型…尚未查驗」一句〕
已查證：
- Gemma 4 採 Apache 2.0 授權。
- Ollama 提供 gemma4:e2b 與 gemma4:e4b；Ollama 頁面列的下載大小分別約 4.6 GB、6.6 GB 起，依標籤與量化版本而異，僅供參考。
- Ollama 支援以 JSON schema 約束輸出格式。
〔改〕成本與部署：不需逐次支付雲端推論費用，也不需租用遠端伺服器；但需要合適硬體、安裝 Ollama、下載模型。Ollama 與遊戲都以本機 HTTP 服務執行。
離線運作的宣稱條件：README 記錄 Ollama 版本、模型名稱與 ID（`ollama list` 顯示）、安裝與取得方式、授權連結；遊戲本體、字型、圖檔全部本機載入，不用 CDN。〔新〕另須實測：下載安裝完成後斷網，冷啟動並跑完一條流程。條件達成前，文章不宣稱離線運作，也不宣稱掌櫃會「跟遊戲一起留下來」。
待實測（使用者電腦）：延遲與輸出品質。實測前不承諾五秒回應，也不保證截止前做完。

## 視覺與回訪
修復前是敵意與失序；修復後是有秩序的詭異，不全面轉為陽光或暖色。
至少顯示：燈亮、雜物清除、桌椅落位、煮茶區運轉、鬼客停留。
〔改〕比賽版以一張靜態場景加狀態圖層呈現上述變化；可有光暈、蒸汽等低成本效果，不做角色動畫。
掌櫃保留非人輪廓，影子可自動添茶。此為美術目標，不保證比賽版已製作動畫。
〔改〕回訪不需等真實隔天：按「離開茶館」再「返回」即可觀察生活場景，不消耗時間與資源。掌櫃與鬼客的位置以靜態圖層切換呈現（例如櫃檯／門邊／座位），不播放行走動畫。

## 驗證〔改：分兩層〕
### 規則層：自動測試，不靠影片
- 三項修復的六種順序 × 候客區兩種位置，全部能完成。
- 無效行動、未知事件 id、過期提案被拒絕或捨棄，且不改動狀態。
- 〔新〕逾時後才到的回應不套用；同一時間不會有第二個有效請求。
- 模型逾時或格式錯誤時遊戲可繼續，成果不遺失。
- 已完成的修復不會被任何回應覆寫或倒退。
- 恢復階段只隨里程碑前進，不跳階、不倒退。

### 模型層：真實本機模型，少量案例、重複執行
- A：燈 → 座位 → 茶具。鬼客在場、座位已好、尚無茶可奉。
- B：燈 → 茶具 → 座位。第一步與 A 相同，測第二步順序造成的行為差異。
- C：茶具 → 座位 → 燈。掌櫃先恢復煮茶，點燈後才出現待客事件；與 A 比較不同歷史。
- E〔改〕：只修好燈、鬼客停在門口時，玩家表達三種意圖：接待、暫候、不介入；每種意圖至少兩種措辭。分開驗證兩件事：模型能否辨別不同意圖；同一意圖換句話說後是否仍一致。
  - 可接受的行動：接待 → 在門邊接待、走向門口；暫候 → 請客人稍候；不介入 → 留在櫃檯、不行動。
  - 此時候客區未完成，「請進」不能要求「邀請入座」。模型選擇合法替代並說明當下能做什麼，不判失敗。
- D：重播 A 的同一份事件資料至少三次；措辭可變，但不得改寫事實。
- A、B、C 與 E 的每組措辭，各至少跑三次。
- 每次記錄真實輸入、輸出、引用事件、行動驗證結果、耗時，並人工標記：引用是否支持台詞、是否把猜測說成事實。
- 與固定腳本基準比較：模型是否能理解不同自然說法，並在限定動作中產生情境一致的回應，而非僅換台詞。
- Demo 影片只節錄片段，不等於測試結果。

## 通過與停損
必須通過：
- 玩家不靠提示能完成至少一項修復，且能指出場景變化。
- 不同順序至少呈現一個可解釋的事件或角色行為差異。
- 〔改〕不捏造事件分兩層：
  - 模型輸出不能直接寫入世界狀態；只有通過驗證的行動，才能由規則系統執行並產生事件。模型不能修改歷史紀錄、修復成果或資源事實。硬性要求，由程式保證並由規則層測試驗證。
  - 自由台詞的語意違規：如實報告觀測次數與限制。有限案例中沒發現違規，不寫成模型不會幻覺。
- 全部測試路徑均可完成；模型出錯或逾時不丟失成果、不鎖進度。
- 使用者願意繼續修第二處，而非僅認為設定合理。此項需實際回饋，不能以助手評分替代。
〔新〕真人試玩：規則層可完整遊玩後就找人試玩（預計週四），不等到發文前。
暫定延遲目標：對話有即時等待提示，5秒內出回應為目標；10秒逾時進降級。這是驗收目標，非既有量測。
若操作只是重複點擊，先改互動；若模型只換台詞，先改角色系統或重新評估AI方案，不以增加居民掩蓋。
〔新〕比賽停損：
- 週四結束前，不接模型仍無法從頭玩到完 → 縮成兩項修復，測試矩陣同步縮減，不保留名義上的驗收數量。
- 〔改〕週五結束前，模型層無法穩定提出合法行動 → 先縮小行動選單到「在門邊接待／請客人稍候／請求協助」等少量、容易驗證且仍有可見差異的行為，而不是全部移除。若仍不穩定，重新評估投稿版本的核心與文章主張；只剩台詞的降級不算通過原設計驗收。

## 時程〔新〕
第一個技術里程碑（週三）：送出一份固定茶館狀態 → Ollama 回傳結構化結果 → 驗證行動 → 更新一個靜態角色位置。這條鏈跑通前，不往下堆場景。模型能力測試與串接測試是兩件事，兩者都在週三做。
- 週三：在使用者電腦跑模型能力測試與串接測試；建 repo；同時做規則層與自動測試。
- 週四：場景與三項修復串起來，不接模型可完整遊玩；真人試玩。
- 週五：接 Gemma、跑模型層測試；依試玩回饋修改。
- 週六：錄 demo、寫英文文章初稿。
- 週日 14:59 前：潤稿、發文。
